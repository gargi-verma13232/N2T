## 6. Implementation Explanation

### 6.1 Screen Memory Geometry
The Hack computer display consists of a $512 \times 256$ monochrome raster grid mapped to RAM addresses $16384$ through $24575$:
- Total words = $8192$ ($256\text{ rows} \times 32\text{ words/row}$).
- Each word represents 16 consecutive horizontal pixels. Bit 0 represents the leftmost pixel and bit 15 represents the rightmost pixel.
- To set all 16 pixels black, write $-1$ (`0xFFFF` or `1111111111111111`).
- To clear all 16 pixels to white, write $0$ (`0x0000` or `0000000000000000`).

For student personal number $K = 23$:
$$\text{Starting Screen Row} = 23$$
$$\text{Height} = 20\text{ rows (rows 23 through 42)}$$
$$\text{Width} = 16 \times ((23 \bmod 4) + 1) = 16 \times 4 = 64\text{ pixels (4 words)}$$
$$\text{Row Address}(r) = 16384 + 32 \times r$$
$$\text{Starting Base Address} = 16384 + 32 \times 23 = 17120$$

### 6.2 Assembly Algorithm Architecture
The assembly program is structured into three cooperating modules:
1. **Keyboard Polling (`POLL_KEYBOARD`):**
   ```hack
   @KBD
   D=M
   @SET_BLACK
   D;JNE
   ```
   Reads memory location $24576$. If $D \neq 0$ (key pressed), jumps to `SET_BLACK`, setting variable `color = -1`. If $D = 0$ (key released), falls through to `SET_WHITE`, setting variable `color = 0`.
2. **Row Loop Setup (`RENDER`):**
   Initializes pointer `row_ptr = 17120` and counter `rows_left = 20`.
3. **Nested Column Loop (`ROW_LOOP` and `COL_LOOP`):**
   For each scanline:
   - Sets `col_ptr = row_ptr` and counter `cols_left = 4`.
   - In `COL_LOOP`: writes `color` into `RAM[col_ptr]`, increments `col_ptr = col_ptr + 1`, and decrements `cols_left`.
   - Once all 4 words are written, jumps to `NEXT_ROW`.
   - `NEXT_ROW` advances `row_ptr = row_ptr + 32` (stepping down to the next scanline) and decrements `rows_left`.
   - When all 20 rows are finished, jumps back to `POLL_KEYBOARD`.

### 6.3 Performance & Zero-Flicker Design
Unlike the classic `Fill.asm` program which repaints the entire 8,192 words of the display on every iteration, our program updates **only the 80 words ($20 \text{ rows} \times 4 \text{ words}$)** belonging to the box. This makes the drawing and clearing cycle run in fewer than 600 machine instructions, providing instant response with zero display flicker.

## 10. Errors Encountered & Debugging Experience
### Genuine Mistake: Non-Canonical ALU Syntax (`M=M+D` vs `M=D+M`)
- **Occurrence:** When compiling the first version of `Box.asm`, our assembler halted with the error:
  ```
  Error at line 99 in 'M=M+D': Invalid computation field 'M+D'
  ```
- **Why it occurred:** In the Hack CPU architecture, the ALU $x$-input is wired to the D-register and the $y$-input is wired to either A or M. While integer addition is mathematically commutative ($M+D = D+M$), the strict Hack instruction specification defines the comp string as `D+M`.
- **How it was fixed:** 
  1. Updated `Box.asm` at line 99 to use the standard canonical instruction `M=D+M`.
  2. Enhanced our Python assembler's `COMP_TABLE` to recognize commutative aliases (`M+D`, `A+D`, `M&D`, etc.) for robustness.
  3. Re-ran assembly, achieving 100% clean compilation.
